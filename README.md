# ArchBench: 8 задач на соблюдение архитектурных правил

Проверяем не «работает ли код», а соблюдены ли архитектурные договорённости
существующего проекта, когда функционально задача уже решена.

В каждой задаче есть исходный проект, описание доработки, функциональные тесты,
отдельно записанное архитектурное правило с проверкой, корректное решение и решение
с намеренным нарушением. Нарушающее решение проходит все функциональные тесты и
падает только на целевом правиле.

| ID | Проект | Доработка | Правило | Проверка | Нарушение |

| `t3_acyclic_reminders` | Бронирование отелей | Актуальные данные в напоминании | Граф сервисов без циклов | `acyclic` из AACT, граф из `deploy/` | `notifications-api` обращается к `bookings-api` |

## Устройство задачи

    tasks/<id>/
      issue.md          описание доработки, правило в нём не упоминается
      repo/             исходный проект; договорённости записаны в docs/adr и схеме
      hidden_tests/     скрытые функциональные тесты
      arch/rule.md      архитектурное правило и способ его проверки
      arch/check.py     сценарий архитектурной проверки, если задан в task.yaml
      task.yaml         какие правила запускать, что считается нарушением
      solutions/        correct.patch и violating.patch

Агент получает `issue.md` и `repo/`. Остальное ему не показывают. Правило можно
узнать только из самого проекта, как это и бывает в реальной работе.

## Запуск

    uv venv --python 3.12 .venv && uv pip install -p .venv -r requirements.lock
    npm install
    .venv/bin/python bench/validate.py               # матрица по всем задачам
    .venv/bin/python -m pytest bench/tests           # проверка самого чекера
    .venv/bin/python bench/archcheck.py <каталог> tasks/<id>/task.yaml

`archcheck.py` завершается с кодом 0 (соответствует), 1 (нарушение) или 2 (не удалось
определить). Чтобы взять AACT из исходников, а не из npm, задайте `AACT_SRC=<путь>`.

## Прогоны агентов

    .venv/bin/python bench/run_agent.py --tasks all --models claude-haiku-5-5 \
        --conditions no_adr,adr_in_repo,adr_in_prompt --repeats 3
    .venv/bin/python bench/report.py                 # сводка в reports/summary.md
    .venv/bin/python bench/report.py --reevaluate    # пересчитать всё из patch.diff
    .venv/bin/python bench/evaluate.py <id> <patch>  # оценить один патч

Агент сейчас один: Claude Code в режиме без интерфейса (`claude -p`). Он получает
копию `repo/` во временном каталоге вне набора. Личные настройки, память, плагины,
MCP и skills отключены (`--safe-mode`). Инструменты: чтение, правка и запись файлов,
поиск и разрешённые команды оболочки (`python`, `pytest`, `git`, `ls`, `cat`, `grep`…).
Всё остальное, в том числе чтение вне рабочего каталога, отклоняется автоматически.

Условия эксперимента:

| Условие | Что видит агент |
| ------- | --------------- |
| `no_adr` | проект без `docs/adr/`; метки в `deploy/` и схема остаются |
| `adr_in_repo` | проект как есть, правила нужно найти самому |
| `adr_in_prompt` | проект как есть и текст ADR в промпте |

Сводка пилота на исходных пяти задачах (45 прогонов) лежит в [reports/summary.md](reports/summary.md).
Артефакты каждого нового прогона сохраняются локально в `runs/<id>/`: `config.json` (задача, модель, условие,
хеши задачи и промпта, коммит набора, версии инструментов), `prompt.md`,
`transcript.jsonl` (полный лог агента), `agent.json` (шаги, стоимость, вызовы
инструментов, отклонённые действия, читал ли агент ADR), `patch.diff` и `eval.json`.
Метрики считаются только из `patch.diff`, поэтому результаты можно пересчитать без
повторного вызова модели.

Перед оценкой `tests/` и `devtools/` возвращаются к исходному виду, так что пройти
тесты, поправив их, нельзя. Правки существующих файлов обвязки записываются в
`harness_modified`, собственные тесты агента — в `tests_added`.

Метрики `report.py`: M1 — доля функционально решённых прогонов; M2 — решено и без
нарушений; M3 — доля нарушений среди функционально решённых; U — доля решённых, где
проверка не смогла вынести вердикт. Разброс считается между повторами.

## Что проверяет `validate.py`

| Вариант | Существующие тесты | Тесты доработки | Архитектура |
| ------- | ------------------ | --------------- | ----------- |
| исходный проект | проходят | падают | проходит |
| `correct.patch` | проходят | проходят | проходит |
| `violating.patch` | проходят | проходят | падает только целевое правило, виновник ожидаемый |

Для задач на сервисах дополнительно проверяется, что схема исходного проекта
соответствует `deploy/`: агент не должен читать неверную документацию.

## Как устроена проверка

В задачах t1–t5 модель строится из `deploy/*.yaml` или из импортов Python.
Модель передаётся правилам AACT. В t5 схема служит второй моделью для сравнения.

В t6–t8 `archcheck.py` запускает сценарий из `arch/check.py` в отдельном
процессе. Сценарий вызывает код из оцениваемого проекта и возвращает JSON-список
найденных нарушений. Ошибка сценария, тайм-аут или неверный JSON дают статус
`error`. Сценарии покрывают заданные комбинации версий, отказов и объёмов входа.

Сервисы запускаются отдельными процессами, адреса заменяются только для объявленных
в `deploy/` зависимостей. Связь, которой нет в конфигурации, просто не заработает, поэтому
функциональные тесты и архитектурная модель опираются на один и тот же факт.

Неизвестное не считается отсутствующим (глава 9.6 книги). Проверка завершается
ошибкой при нечитаемых манифестах и схемах, адресах в коде, импорте чужого сервиса,
прямом `sqlite3`, динамических импортах и смене архитектурной метки существующего
сервиса.

## Ограничения

- Проекты синтетические и написаны специально для набора. Для основного эксперимента
  нужны реальные репозитории.
- Проверка видит структуру связей, но не содержимое. Адаптер с бизнес-логикой внутри
  правило `acl` не поймает.
- Обращения через рефлексию и общие объекты времени выполнения проверка не отслеживает.
- Сейчас по одному нарушению на правило; на прогонах агентов появятся другие.
- Пока измеряется связка «Claude Code + модель Claude», а не модель сама по себе.
  Чтобы сравнивать модели разных провайдеров, нужна одна общая обвязка.
- Составные команды оболочки (циклы, `&&`) не подходят под разрешённые шаблоны и
  отклоняются. Агент обходит это через инструмент чтения файлов, но отказы
  записываются в `agent.json`.

AACT (GPL-3.0) подключается как зависимость и в набор не входит.
