# ArchBench: пилотный набор из 5 задач

Проверяем не «работает ли код», а соблюдены ли архитектурные договорённости
существующего проекта, когда функционально задача уже решена.

В каждой задаче есть исходный проект, описание доработки, функциональные тесты,
отдельно записанное архитектурное правило с проверкой, корректное решение и решение
с намеренным нарушением. Нарушающее решение проходит все функциональные тесты и
падает только на целевом правиле.

## Задачи

| ID | Проект | Доработка | Правило | Проверка | Нарушение |
| -- | ------ | --------- | ------- | -------- | --------- |
| `t1_acl_delivery` | Заказы маркетплейса | Стоимость доставки у внешнего перевозчика | Внешние системы только через адаптер | `acl` из AACT, граф из `deploy/` | `orders-api` зовёт перевозчика напрямую |
| `t2_passive_repo_cap` | Программа лояльности | Месячный лимит баллов по уровню клиента | Репозиторий связан только со своей БД | `crud` из AACT, граф из `deploy/` | `loyalty-repo` сам запрашивает уровень клиента |
| `t3_acyclic_reminders` | Бронирование отелей | Актуальные данные в напоминании | Граф сервисов без циклов | `acyclic` из AACT, граф из `deploy/` | `notifications-api` обращается к `bookings-api` |
| `t4_module_contracts_hold` | Модульный монолит магазина | Резерв на одном складе | Модули общаются только через контракты | Своё правило `bcIsolation` в формате AACT, граф импортов | Заказы импортируют `inventory/internal` |
| `t5_schema_drift_scan` | Обработка документов | Антивирусная проверка | Схема соответствует системе | `computeDiff` из AACT: схема против `deploy/` | Новый адаптер не внесён в схему |

## Устройство задачи

    tasks/<id>/
      issue.md          описание доработки, правило в нём не упоминается
      repo/             исходный проект; договорённости записаны в docs/adr и схеме
      hidden_tests/     скрытые функциональные тесты
      arch/rule.md      архитектурное правило и способ его проверки
      task.yaml         какие правила запускать, что считается нарушением
      solutions/        correct.patch и violating.patch

Агент получает `issue.md` и `repo/`. Остальное ему не показывают. Правило можно
узнать только из самого проекта, как это и бывает в реальной работе.

## Запуск

    pip install -r requirements.txt
    npm install
    python bench/validate.py                         # матрица по всем задачам
    python -m pytest bench/tests                     # проверка самого чекера
    python bench/archcheck.py <каталог> tasks/<id>/task.yaml

`archcheck.py` завершается с кодом 0 (соответствует), 1 (нарушение) или 2 (не удалось
определить). Чтобы взять AACT из исходников, а не из npm, задайте `AACT_SRC=<путь>`.

## Что проверяет `validate.py`

| Вариант | Существующие тесты | Тесты доработки | Архитектура |
| ------- | ------------------ | --------------- | ----------- |
| исходный проект | проходят | падают | проходит |
| `correct.patch` | проходят | проходят | проходит |
| `violating.patch` | проходят | проходят | падает только целевое правило, виновник ожидаемый |

Для задач на сервисах дополнительно проверяется, что схема исходного проекта
соответствует `deploy/`: агент не должен читать неверную документацию.

## Как устроена проверка

Модель строится по тому, что реально лежит в решении, а не по схеме: из
`deploy/*.yaml` или из импортов Python. Модель передаётся настоящим правилам AACT.

Сервисы запускаются отдельными процессами, адреса заменяются только для объявленных
в `deploy/` зависимостей. Связь, которой нет в конфигурации, просто не заработает, поэтому
функциональные тесты и архитектурная модель опираются на один и тот же факт.

Неизвестное не считается отсутствующим (глава 9.6 книги). Проверка завершается
ошибкой при нечитаемых манифестах и схемах, адресах в коде, импорте чужого сервиса,
прямом `sqlite3`, динамических импортах и смене архитектурной метки существующего
сервиса.

## Ограничения

- Проекты синтетические и написаны специально для набора. Для основного эксперимента
  нужны реальные репозитории.
- Проверка видит структуру связей, но не содержимое. Адаптер с бизнес-логикой внутри
  правило `acl` не поймает.
- Обращения через рефлексию и общие объекты времени выполнения проверка не отслеживает.
- Сейчас по одному нарушению на правило; на прогонах агентов появятся другие.

AACT (GPL-3.0) подключается как зависимость и в набор не входит.
